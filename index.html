How it works

One screen, two of you

Your agent keeps working in your terminal or editor. CodeDiver is the screen you share: it shows the agent where you are, and shows you what the agent means.

  1. 1

    It sees what you see

    The agent knows the file, line, selection and function you have open. Ask about “this function” and it knows which one.

  2. 2

    It shows instead of tells

    Animated demos, walkthroughs, function logic and call paths open on your screen, linked to the real code. Demos →

  3. 3

    It proposes. You decide.

    Changes arrive as visual proposals with their blast radius. Accept, reject or send feedback, file by file. Decide →

  4. 4

    You check the work together

    See what the tests actually cover, where the risky gaps are, and agree on a test plan before it's written. Test →

Demos New in v0.2.0

Ask for a demo, get one

Ask “show me how a request moves through our CDN” or “animate how a sensor reading gets encoded”, and your agent builds an animated, step-by-step demo on your screen.

  • Architecture that looks the part — regions, data centers and services nested inside each other, with icons, color-coded paths and labels that keep out of each other's way.
  • Watch it move — packets travel the real routes, values change on each box, and the camera follows the action. Play, pause, step, or zoom and pan yourself.
  • Tied to your code — click a box to open the function it stands for; each step can show the code behind it.
  • Export and share — any step as PNG or SVG, the whole demo as a PDF with the narration. Agents can export images too, to check their own work.

Explain

Understand any part of the code, together

Ask “walk me through how a request reaches the database” and your agent builds a guided tour you can step through at your own pace.

  • Every step is real code — opened, highlighted and explained in place, with code lenses showing callers and callees.
  • A map of the path shows where you've been and where you're going.
  • Keyboard-driven — arrow keys move between steps; jump into any function's logic or trace from there.
  • Reusable — tours stay in the Agent panel for the session, so you can revisit them.

The point isn't for the agent to know your codebase. It's for you to.

Walk me through this change

Before you accept a change, or after someone merges one, ask your agent to tour it. It visits each changed function in the order that makes sense: the cause, the fix, and the test that proves it, each highlighted in the real code with a map of where you are.

Review a change by understanding it, not by scrolling a diff.

Diagrams that point back to code

Agents can draw sequence, flow, class and state diagrams with Mermaid — or interactive graphs whose nodes open the code they describe. Architecture stops living only in someone's head.

Decide

Shape the change before it lands

Agents submit changes as proposals, and nothing touches your code until you accept. You review them visually, and your feedback goes straight back for the next round.

  • Side-by-side diffs with the agent's rationale for every file.
  • Blast radius, closest first — direct callers in full, callers further out grouped by package, and the entry points the change reaches. Each caller says whether a test runs its call into the change, so you know what to check before you accept.
  • Tests for the change — which changed lines tests run and which they don't, marked in the diff. Click Run these tests (Go and pytest) to see which test runs which line.
  • Accept or reject per file, with feedback that goes straight back to the agent.
  • Conflict-safe — if the file changed since the proposal, CodeDiver refuses to overwrite it.

Which tests cover the change

Next to every diff: how many changed lines tests run, which lines no test runs, and the tests that call or reach the changed code. Click Run these tests to measure which test runs which line, or ask your agent to write the missing ones.

Agents see the same report with get_tests_for_change, for a proposal, the working tree or any commit.

Test Improved in v0.2.0

Know what your tests actually cover

Agents write tests fast. CodeDiver shows you whether they test what matters, and what's still exposed.

  • Real line coverage from your own tooling: Go, Vitest, Jest, pytest, RSpec, Cargo, Maven, Gradle and .NET are detected, or import an LCOV, Cobertura, JaCoCo or Go report you already have.
  • Gaps ranked by risk: uncovered code weighted by complexity and how many callers depend on it.
  • Why it's hard to test: hard-wired clocks, network, filesystem, env vars, processes and sleeps, each with the refactor that fixes it.
  • Tests that reach it, directly or through its callers, so you don't write the same test twice.

Reviewing a change? Its tests and their coverage open next to the diff. See Decide →

Your agent plans the tests. You approve them.

Ask “what isn't tested here?” and your agent reads coverage over MCP, then puts a test plan on your screen: the behaviors to cover as given / when / then, tied to the lines they exercise, plus any refactor the code needs first. When you agree, it proposes the tests as a change set you review.

Coverage runs happen only when you click Run. Agents read the results; they can't run commands.

Get started

Up and running in three steps

  1. 1

    Add your repository

    CodeDiver indexes it locally — call graphs, types, control flow, git history. Nothing leaves your machine.

  2. 2

    Connect your agent

    One command adds CodeDiver as an MCP server. Your agent can now see the code the way you do — and show you things.

    claude mcp add --transport http --scope user codediver http://127.0.0.1:47474/mcp
  3. 3

    Ask, watch, decide

    Ask “walk me through this” or “fix that bug”. The agent opens views in front of you, explains as it goes, and proposes changes you accept or reject.

Connect

Works with the agent you already use

CodeDiver runs a local MCP server with 35 tools for seeing, explaining, proposing and testing. Add it to your agent with one line.

Connect in one line

CodeDiver runs a local MCP server at http://127.0.0.1:47474/mcp. Stdio-only clients use the built-in bridge: codediver mcp.

claude mcp add --transport http --scope user codediver http://127.0.0.1:47474/mcp
// ~/.cursor/mcp.json
{ "mcpServers": { "codediver": { "url": "http://127.0.0.1:47474/mcp" } } }
// .vscode/mcp.json
{ "servers": { "codediver": { "type": "http", "url": "http://127.0.0.1:47474/mcp" } } }
// claude_desktop_config.json
{ "mcpServers": { "codediver": { "command": "codediver", "args": ["mcp"] } } }
# ~/.codex/config.toml
[mcp_servers.codediver]
command = "codediver"
args = ["mcp"]

Safety model

You decide what the agent sees and changes

  • 01
    Only the repos you add. Each one can be hidden from agents with a switch.
  • 02
    A real sandbox. No .. or symlink escapes; .git, .env*, keys and your own globs are invisible.
  • 03
    No silent writes. The only way to change code is a proposal you accept.
  • 04
    No commands from agents. Test and coverage runs start only when you click Run; agents just read the results.
  • 05
    Local only. Bound to 127.0.0.1, protected against DNS rebinding and cross-site requests. Your code never leaves your machine.
